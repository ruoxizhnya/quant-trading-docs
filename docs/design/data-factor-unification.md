## 1. 背景：一次定位分歧，一次路线裁决

### 1.1 分歧事实（记录在案，防再漂移）

ADR-031 落地的 NT 侧车是**窄定位**：「权重回放 + A 股最小规则」的**执行对拍考官**——只喂 OHLCV + 目标权重，不碰因子、不做选股，K15 双跑验完即收口。

但**引入 NT 的本意是宽定位**：NT 是世界级交易引擎，应**全 feature 被应用**，作为**完整第二核心**——国内市场用 Go 全栈、国外市场用 NT 全栈，按市场**热转换**。

两种定位都成立（前者是「A 股执行可信度」动机的产物，后者是「引擎资产利用」动机），但走的是两条路。会话中按窄定位解释架构时产生持续误解，故先钉死路线再谈细节。

### 1.2 路线裁决：路线二 ✅ 已拍板

> **按市场切完整核心**——国内 Go 全栈（策略 + 执行），国外 NT 全栈（Python 策略 + 原生执行），**外壳共用**（RunSpec 路由、ResultSpec 回执、审计、UI）。这才是「双核热转换」。

配套三条（同会话拍板）：

- **NT 全 feature**：国外线用足 NT 的数据模型、指标库、流式策略框架、原生市场支持（美股/加密等），不做「只当考官」的自我设限。
- **国外市场策略直接用 NT 原生写**：Go 策略资产全是 A 股逻辑（T+1、涨跌停感知），本就不适配国外市场；国外策略是**新增**而非重写，天然规避 ADR-031 否决方案 A 的「策略重写 6–12 人周」包袱。
- **调度层地基已在**：四契约的 RunSpec 本就带内核选择字段（kernel=go / kernel=nautilus，未知内核 fail-loud），ResultSpec 归一化回执、审计、UI 与内核无关——外壳共用不是新建，是已建成。

### 1.3 双核对齐语义的分层（重要澄清）

会话中厘清的对齐语义，两层不要混：

| 层 | 内容 | 正确性手段 |
|---|---|---|
| **想法**（因子 → 目标权重） | 因子计算、策略决策 | **一份逻辑**，靠单元测试（数学定义钉死）+ 研究验证（IC、分组收益）保真 |
| **动作**（目标权重 → 成交） | 下单、撮合、持仓核算 | **两份实现**（Go / NT），靠双跑对拍验真（K15 ≤0.2%） |

- 分界线 = **目标权重**。对拍只在「有客观标准」（T+1、涨跌停、手数是交易所规则）的地方才有裁判意义；因子是独有逻辑、无第三方标准答案，两份逻辑互检只验出「抄得一致」，验不出真伪——**明确不做「让 NT 重算因子来对拍」**。
- 路线二落地后，国外线 NT 全栈（策略也在 NT）时对拍不再是唯一目的——各市场独立运行，外壳共用保障的是**审计、UI、结果口径**的一致，不是逐笔对齐。

## 2. 目标架构总览

```
                    ┌────────── 外壳（两线共用）──────────┐
                    │ RunSpec 路由（kernel 选择）          │
                    │ ResultSpec 归一化回执 / 审计 / UI     │
                    └──────────────┬───────────────────┘
                                   │
              ┌────────────────────┴────────────────────┐
              │                                         │
      【国内线 · Go 全栈】                        【国外线 · NT 全栈】
      行情/财报/因子 → 策略决策 → 执行          NT 原生：数据 + 指标 + 策略 + 执行
      （现状保持，四契约不变）                   （新增 NT 原生模式，全 feature）
              │                                         │
              └────────────── 规范层 ───────────────────┘
                    （统一数据 schema，唯一真相）
                    connector → 规范层 → 按内核翻译
```

**数据主干**（本文核心新增）：

```
【原始层】connector 拉来的原样数据（Tushare JSON / NT Parquet / 新源任意格式）
    ↓  connector 自带翻译（每源一个适配器，模式见 §4.4）
【规范层】统一内部 schema ←—— 唯一真相，频率/时间语义自带（§4.1/§4.2）
    ↓  按内核翻译
  ├─→ Go 内核：直接吃（规范层 schema 由 Go 侧定义，不被 NT 反向污染）
  └─→ NT 内核：翻译成其数据模型（Bar/BarType/自定义数据类，现有 export_bars 映射是第一条实现）
```

- **因子与策略决策永不跨边界翻译**：交接的只有目标权重（信号）+ 规范化数据。NT（国外线全栈模式除外）不感知因子。
- **国内线 NT 侧车现状不变**：仍是权重回放对拍，作为执行段可信度的持续保障。

### 2.1 热转换语义（"热"字的准确含义）⚠️ 必须钉死

「热转换」不是运行中无缝切引擎，而是**切换成本 = 配置级**：

1. **切换载体 = RunSpec 的 `kernel` 字段**（四契约既有字段）：`kernel=go` / `kernel=nautilus`。**同一份 ResultSpec 回执**，前端/审计不感知内核差异。
2. **切换粒度 = 按市场路由**（配置驱动，零代码改动）：市场维度 → 内核的映射写在配置（如 `market.US → nautilus`、`market.CN → go`），新市场接入 = 加一条配置 + 对应数据 connector，**不改路由代码**。
3. **fail-closed 语义继承**：未注册的内核名/市场映射 → 显式拒绝（400/error），不静默回退到 Go 内核——这是 K0 冻结的 EngineRunner 语义，热转换不放松。
4. **不做"运行中无缝迁移"**（一次 run 中途换引擎）：无此需求，且破坏可复现。"热"= 部署配置级，不是 run 级。
5. **四契约就是拆仓的缝**（见 §10 与 §9 未决 #7 的归口讨论）：RunSpec/SignalSpec/ResultSpec/EngineRunner 既支撑双核路由，也是将来服务/仓库边界的接口面——**契约先冻结，物理拆分随时可做**。

### 2.2 性能红线（拆分/热转换的前置约束）

- **高频路径绝不跨进程**：回测主循环逐 Bar 调用（provider 取数、信号求值、撮合）**必须进程内函数调用**——一次 HTTP 往返会把双核对拍的延迟和噪声放大到不可用。
- **低频路径才允许跨进程**：run 级提交/回执、因子定义拉取（开跑前 1 次，不是 per-day）、connector 数据同步。
- **per-day HTTP 陷阱**（ADR-027 已踩过一次并记档）：「每天把全市场数据 POST 给另一个服务算信号」是错的方向——**传定义，不传数据/信号**。
- **不允许为了"性能"绕过规范层直连 DB**（ADR-027 同款红线）：一旦绕过，归一化 schema 名存实亡。

## 3. 双核职责表（路线二终态）

| 信息/能力 | 国内线 Go | 国内线 NT（对拍） | 国外线 NT（全栈） |
|---|---|---|---|
| 因子计算 / 策略决策 | ✅ 独占 | ❌ 不感知 | ✅ NT 原生（Python 策略） |
| 目标权重（信号） | ✅ 产出 | ✅ 收到（照做） | ✅ 内部产出并执行 |
| 行情 OHLCV | ✅ 思考用（决策输入） | ✅ 干活用（定价/涨跌停/日历） | ✅ 原生数据通道 |
| 下单/撮合/持仓 | ✅ | ✅（双跑对拍） | ✅ 原生规则（美股/加密等） |
| 交易规则 | A 股内置（T+1/涨跌停/手数） | A 股最小规则（对拍） | NT 原生（各市场自带） |

**一句话**：国内线想法和动作都在 Go（NT 只验动作）；国外线想法和动作都在 NT（全 feature）；外壳把两线统一成一个产品。

## 4. 数据归一化 Schema（规范层）

### 4.1 规范层定位

- **唯一真相**：connector 的职责是「把自家格式翻译进规范层」，此后全系统只认这一种格式。与现 ETL 的溯源列 + 幂等重放套路同源，提升为显式契约。
- **schema 由 Go 侧定义**：规范层是唯一被两边都消费的口径，NT 翻译是适配责任，不得反向污染规范层。
- **翻译层只在内核边界存在**：现有 nt-sidecar 的 Parquet 导出映射（export_bars）是第一条实现；加新数据类 = 映射表加一行。
- **频率是数据自带字段**（`frequency`：1d / 1m / 15m…），不靠来源表隐式区分——这是现状（domain.OHLCV 无频率字段、靠表名区分）要补的第一刀。

### 4.2 时间语义红线（point-in-time）⛔ 最高优先级

行业血泪纪律（Databricks / SageMaker Feature Store 的核心机制）：**每条数据必须自带「什么时候才可见」的时间戳**，查询永远按「当时的视角」取数，否则即数据泄漏——且**极难事后发现**（回测曲线照样漂亮）。

**裁定**：

1. connector 注册的 schema 里**必须声明时间语义**（按公告日可见 / 按收盘后可见 / 按次日开盘可见 / …），声明不了或声明错了 → **fail-closed 拒收**。
2. 同级必填：**频率口径**（日频 / 分钟频 / 事件流；日内数据按什么聚合成日频）——口径不定死，双跑对齐无法做。
3. 高危示例（用户点名的场景）：**市场活跃度、拥挤度**类数据——活跃度要收盘后才统计得出，若回测里 3/5 盘中就用「3/5 全天的活跃度」即偷看当日全天信息。红线优先级**高于因子公式治理**：公式错了算错分，时间泄漏直接废掉整个回测。

### 4.3 频率与存储

现状（已核实）：

| 频率 | 表 | 时间字段 | 数据源 | 回测消费 |
|---|---|---|---|---|
| 日线 | `ohlcv_daily_qfq` | `trade_date`（DATE） | Tushare | ✅ 唯一进回测的 |
| 1 分钟 | `ohlcv_minute` | `ts`（TIMESTAMPTZ） | mootdx | ❌ 只存着 |
| 15 分钟 | 无 | — | — | 靠 1m 聚合 |

**裁定**：

1. **存储沿用按频率分表**（业界惯例）：量级差一个数量级（分钟=日线×240）、时间语义不同（DATE vs TIMESTAMPTZ）、保留策略不同（分钟可只留近期）。规范层提供**透明路由**——调用方说「要 15 分钟线」，不需知道存在哪张表。
2. **反例分界经验**（写进规范层设计）：同类数据小量聚合周期可混表（`capital_flow` 用 `period` 列区分日内/日/周），量大或时间语义不同的频率必须分表。
3. **聚合规则成文**：1m → 15m → 1d 口径（开=首笔开、高=期间最高、低=期间最低、收=末笔收、量=期间合计）写进契约——这是双跑对齐的翻译点之一。
4. **多频率进回测是设计中事**（当前只支持日线回测）：策略视野建议「日频决策 + 可引用当日内分钟特征」（如开盘半小时动量），引擎撮合精度升级（分钟级撮合）另立工单；分钟级防偷看闸门按分钟粒度设（10:00 的 1 分钟线 10:01 才可见）。

### 4.4 connector 注册机制（数据热插拔）

- **现有雏形**：cmd/data registry_init 的 adapter 注册 + kill-switch（缺依赖降级不阻断启动）、溯源列 + 幂等重放。
- **新增内容**：注册契约含「时间语义 + 频率口径」声明（§4.2）+ 映射到规范层 schema 的翻译责任。
- **用法**（用户场景）：挂一个「市场拥挤度」connector → 数据进规范层 → **注册为因子挖掘可用数据** → 新数据即可被因子公式引用（须先有 §5 公式化因子）。

## 5. 因子体系（热插拔）

### 5.1 三元组抽象（用户提出，与米筐 rqfactor 同构）

> **因子 = 数据源 + 计算函数 + 按日分数序列。** OHLCV 也当叶子因子（`Factor('open')` 即「开盘价因子」，米筐原文做法）——策略只看一组因子序列，每因子有自己的 provider / 数据源 / 计算。

- **接口统一、底层分流**（工程保留意见）：OHLCV 是最高频数据，接口层统一为「因子序列」，底层保留行情快车道（不走通用计算通道）——行业同样如此（米筐引用 Factor('open') 但底层行情存储专用）。
- **基本面宽表退化为 12 个叶子因子**（pe/pb/ps/roe/roa/负债权益比/毛利净利率/营收净利/总资产总负债——`stock_fundamentals` 的 12 个数字字段），宽表只是存储优化，接口层一律拉平。「SetFundamentals 给的是什么」问题消失——即「订阅了 12 个财报叶子因子」。
  - ⚠️ **口径辨析**（两个数字别混）：「12 个」= 财报原始字段叶子因子；「11 个」（§6 三期①）= 当前**冻结因子名注册表**里的计算因子（6 通用：momentum/value/quality/size/volatility/growth + 5 纵向：gross_margin_trend/contract_liability_ratio/ocf_to_net_profit/roe_dupont_leverage/inventory_turnover_delta）。三元组化后 12 个叶子 + 11 个计算因子同吃一套 schema。

### 5.2 Schema：一个外壳 + 三种内核

**产出 schema——所有因子一个样**（策略看到的）：

| 字段 | 含义 |
|---|---|
| 因子名 / 日期 / 股票 | 定位三元组 |
| 值 | 分数 |
| 存在性 | **缺失≠0**——「没有」要说出口（0 是有效分数，缺失是数据状态） |
| 口径 | z-score（标准化分）/ rank（百分位）/ raw（原始值）——苹果橘子不可加权混用，现有插件「默认全 z-score」的隐含假设要显式化 |

**定义 schema——骨架一个 + 计算内核三型**（计算层看到的）：

- 公共骨架：名字、**版本指纹**（改公式=新版本，老版本可复现）、生效日、口径、输入依赖、**前视纪律**（按公告日/交易日对齐）。
- 计算内核三选一：**叶子**（原始字段直取）/ **公式**（叶子+算子表达式）/ **代码**（复杂过滤、ML 打分，保留 Go 出口）。

**三条铁律**：缺失可见（见上）；定义带版本指纹（同一回测永远引用同一版定义）；前视纪律进 schema（防偷看从约定变成结构）。

### 5.3 两件热插拔分开

| | 数据热插拔 | 因子热插拔 |
|---|---|---|
| 是什么 | 挂新 connector（§4.4） | 写新因子公式进名册 |
| 靠什么 | 连接器注册表（模式现成） | **公式化因子**（见 §6 三期①） |
| 现状 | 模式有，注册的是数据类型不是任意源 | **未实现**，是三期工单主活 |

两件是同一张蓝图的两半：光有 connector 新数据算不出因子（因子定义还是写死代码）；光有公式因子没新数据也没原料。**必须都做，顺序见 §6。**

### 5.4 因子正确性验证（不靠双跑）

- **单元测试**：数学定义钉死（动量 = 20 日均/现价，固定输入必等手算值）。
- **研究验证**：IC、分组收益——引擎对拍给不了的。
- **明确不做**：让 NT/第二实现重算因子对拍（两份逻辑互检验不出真伪）。

### 5.5 AI 挖掘（第三期）

- 产物是**公式文本**不是代码（LLM+MCTS 公式挖掘、AlphaPilot 等学术路线同此），故能动态加载、即挖即测。
- 流程：AI 生成公式 → 沙箱验证（复用现有沙箱资产）→ 入库（带哈希版本）→ 策略即用。
- 治理层是主要成本：过拟合检测、样本外验证、公式审计留痕。
- 三条命根子在新架构下的落法：公式带哈希锁版本（可复现）、计算走快照（防偷看）、双侧同公式同快照可对拍（可比）。

## 6. 实施路线（分期，每期独立可交付）

**第一张工单（地基，因子线与数据线共同前置）**：
> **规范层 schema + 时间语义红线**——频率字段、时间语义声明契约、按内核翻译层、聚合规则成文。一次设计，长期受益；不做它，后面每张工单都在流沙上。

**因子三期**（顺序：地基 → ①②③）：

| 期 | 内容 | 改动量 | 依据 |
|---|---|---|---|
| ① 公式化因子 | 因子定义从 Go 代码改为库里公式（名字+公式+输入字段+版本哈希），计算线读公式现算/缓存；11 个硬编码因子翻译成公式入库；因子名注册表从「代码冻结」改「库管理」（复用外部门户信号 content_hash 幂等先例） | 小——**引擎现成**（pkg/expression 已有 parser/evaluator/operators/registry，表达式选股就是动态因子引擎），搬运+治理为主 | 米筐/聚宽/WorldQuant 全是此范式（§8） |
| ② 新数据源 connector | 市场活跃度、拥挤度等——每源一个标准适配器（宏观 P2-1 是先例）+ 注册为挖掘可用数据 | 每源一个小工单 | §4.4 |
| ③ 热插拔 + AI 挖掘 | AI 公式挖掘流水线 + 治理层（过拟合/样本外/审计） | 主要在治理层 | §5.5 |

**NT 侧「原生模式」**（路线二关键件）：侧车加 NT 原生模式（数据模型 + 订单类型 + 执行规则，国外市场用足全 feature）——比已做的 A 股适配省事（NT 对美股/加密原生支持，无需规则魔改）。RunSpec 路由已就位，缺的只是这半边能力。

**协议变更纪律**：因子名清单现为代码冻结面，改「注册表管理」是正式契约变更——审计要求更高（每条登记带公式、哈希、登记人、生效日）。

## 7. 明确不做 / 边界

1. **不做「让 NT 重算因子来对拍」**（§1.3/§5.4）——想法层一份逻辑靠测试与研究验证，动作层两份实现靠对拍。
2. **不做「运行时查数据」给策略**（第三档不给，三条命根子：可复现/防偷看/双跑可比）——要新数据走「考前发资料」预取（connector → 规范层 → 快照注入），不给「考中打电话」。
3. **不推翻 ADR-031 既有裁决**：国内线现状（权重回放对拍、四契约、A 股规则）不变；本蓝图是扩展定位，不是回退。
4. **不做「每个因子发明一种 schema」**：产出一个样、定义骨架一个 + 三型内核，不按因子逐个定制。
5. **现状缺口如实记录**：15 分钟线未存储（靠 1m 聚合）、多频率进回测未支持、因子名 11 个冻结——这些都是三期工单要动的，不是既有能力。

## 10. 拆仓 / 服务化评估（2026-10-14 补充研究，大双核架构下复评）

> **问题原话**：core 仓越来越大，长期维护有隐患；要不要把 API 层 / 策略层 / 数据层摘出独立 repo 分别维护？摘出独立 repo 是否意味着要单独做成 service，把内联 communication 变成 HTTP / message queue？如果对性能伤害太大就不能盲目做。
> **一句话答案**：**摘 repo ≠ 必须 service 化**——这是两个独立维度，捆在一起想就只能二选一，其实有第三条路（monorepo + 多 module）。而且这个问题**项目里已有 93KB 的既有裁决**（[ADR-027](https://github.com/ruoxizhnya/quant-trading-docs/blob/main/docs/adr/adr-027-modular-decomposition-to-independent-services.md)，Proposed，2026-10-06，三轮头脑风暴），本节只做「大双核架构下的复评 + 归口」，不推翻它。
> **归口状态**：✅ 已落档（2026-10-14）——本节结论已追加进 ADR-027「复评记录：大双核架构下的拆仓/服务化再评估（2026-10-14 追加）」，ADR-027 为该主题的单一真相；本节保留完整推导过程供参考。

### 10.1 三个概念必须先拆开（用户把它们捆在一起问）

| 维度 | 是什么 | 成本 | **性能影响** | 解决什么问题 |
|---|---|---|---|---|
| **拆模块** | 进程内包边界 + 编译期护栏（`internal/repoguard`） | 低 | **零** | 认知负担、边界腐蚀 |
| **拆 repo** | git 仓库边界（多仓 或 多 module 单仓） | 中（跨仓版本/发布/CI） | **零**（编译期事，运行时调用不变） | 发布节奏差、协作/许可边界 |
| **拆服务** | 进程边界 + 网络调用（HTTP/MQ） | 高（运维/契约版本化/分布式调试） | **有**（每跳一次网络往返） | 独立伸缩、独立部署 |

**关键澄清**：用户担心的「拆 repo 就要变 HTTP/MQ」把 repo 和 service 捆死了。Go 的解法是**多 module 单仓（或 `go.work` workspace）**——编译边界强制（越界 import 直接编译失败，分层从「约定」升格为「编译器强制」），开发仍在同一工作区，**运行时零网络开销**。拆 repo 的收益 80% 来自编译边界，不来自 git 边界。

### 10.2 既有裁决必须先读（ADR-027，用户 2026-10-06 亲裁）

ADR-027 就是这个问题的深度研究，核心结论（**不是新问题，是老裁决的复评**）：

| 簇/层 | ADR-027 裁决 | 依据 |
|---|---|---|
| **①回测核心**（backtest/walkforward/risk/execution/…) | **不拆**——「不是暂时不拆，是判定为不该拆」 | Engine 实例注入 + `AlertHistory` 进程内 ring buffer 共享指针 + walk-forward per-window 独立实例 |
| **②AI 链路** | 拆 ai-service（**已落地**，agent 仓） | `CopilotService` 无共享状态，纽带只是 `BacktestRunner` 接口 |
| **③只读薄壳**（compliance/evidence/…) | 归位 | 零 DB、零 Engine、零共享状态（值拷贝构造） |
| **数据层** | **A/B 二分**，且「6 个限界上下文在 data-service 内部**按包强制隔离，不拆进程**」 | 明文：「拆 7 个服务对单人实验室是**运维灾难**」 |
| **策略层** | 独立成策略服务（§2.6.1）但**只传定义，不传信号** | 「per-day HTTP 陷阱」——每天把全市场数据 POST 出去算是错方向 |
| **落地顺序** | **先做进程内核模块化（P0–P2）**，服务拆分（5→7）在其后，且是「**可选的后续部署形态**」 | 进程内模块契约是服务拆分的直接输入 |

**实测现状**（2026-10-14 复测）：生产 **80,363 行 / 76 包 / 35 个 `pkg/` 目录**（ADR-027 记录时为 78,595 行 / 91 包——AI 摘出后行数微增、包数收敛，说明**拆包方向有效但病根未除**）。

### 10.3 大双核架构带来的新判断（本节增量）

双核蓝图把系统切成「**壳**（RunSpec 路由/ResultSpec/审计/UI）+ **核**（Go 回测执行 / NT 全栈）」，这给了拆仓**一条比 ADR-027 更自然的缝**——四契约（§2.1.5）就是接口面：

```
按「契约」切，不按「层」切：
  壳仓（api 路由 + ResultSpec 消费 + 审计 + UI 消费面）   ← 低频，可 service 化
  核仓（Go 回测执行 + 规范层 + connector）              ← 高频，永不跨进程
  nt-sidecar 仓（已独立，Python）                        ← 先例：发布节奏差是拆 repo 的正当理由
  agent 仓（已独立，AI 链路）                            ← 先例
```

**关键推论**：用户问的「API 层 / 策略层 / 数据层」按**旧分层**切是伪需求——层与层之间是高频调用（逐 Bar 取数、求值），切开必然要付网络税；按**契约**切才是真缝（run 级提交/回执、因子定义拉取、connector 同步——全是低频）。

### 10.4 三步走建议（与 ADR-027 同向，新增 repo 维度）

1. **先拆模块，不拆 repo**：按 ADR-027 的 P0–P2 进程内核模块化走，`internal/repoguard` 护栏 + Go 编译边界强制分层。**80k 行的病根是边界不清，不是仓库不够多**——这一步直接吃掉「认知负担」的大头。
2. **repo 边界按四契约切，且用 monorepo 多 module**：壳 / 核 / nt-sidecar / agent 四个 module，`go.work` 联调。**暂不真拆多 git 仓库**——单人实验室「发布节奏差、协作边界、许可边界」三条真拆 repo 的正当理由都不成立（nt-sidecar 是唯一例外，因为它是 Python、天然独立）。
3. **服务化只在真需要独立伸缩/部署的地方做**（ADR-027 的 5→7 那套），且**只走低频路径**（run 级提交/回执、因子定义拉取、connector 同步）；高频路径（逐 Bar provider/信号/撮合）**永驻进程内**（§2.2 红线）。

### 10.5 判据表（什么时候才真的该拆 repo / 拆服务）

| 触发条件 | 该做什么 | 现在成立吗 |
|---|---|---|
| 跨仓发布节奏差（不同生命周期/不同语言/不同团队） | 拆 repo | ✅ nt-sidecar、agent（已做）；❌ 核/壳（同节奏） |
| 编译边界被反复腐蚀（越界 import 时有发生） | 拆 module + 护栏 | ⚠️ 部分（repoguard 已在，覆盖待补） |
| 单一服务需独立伸缩（回测 CPU 密集 vs API IO 密集） | 拆 service | ❌ 单机未到瓶颈 |
| 分布式事务/一致性需求 | **别拆** | — |
| 单人维护、无独立运维人力 | **别拆 service**（ADR-027 明文「运维灾难」） | ✅ 现状 |
