# ODR-046: Hermes Agent Integration Decision

> **Status**: Accepted
> **Date**: 2026-07-02
> **Category**: Migration
> **Related ADRs**: [adr-015](../../adr/adr-015-ai-agent-architecture.md)
> **Supersedes**: Partial — supersedes the "frontend AI UI" approach in ADR-015 §Dimension 4

## Context

ADR-015 defined an "AI-Native Evolution" architecture with two layers:

1. **Backend agents** (`pkg/ai/agents/`): Go-native ResearchAgent,
   GenerateAgent, ValidateAgent, EvolveAgent — driving the AI pipeline
   (`cmd/ai` service, port 8086).
2. **Frontend UI** (`web/src/components/ai/`): FactorLab, StrategyWorkshop,
   EvolutionObs, etc. — human-in-the-loop research interface.

The backend layer was implemented and is functional. The frontend layer was
**created in P1-13 (ODR-017) then deleted as dead code in S7-P2-7 (ODR-043)**
— see [ODR-045](odr-045-frontend-ai-component-deprecation.md) for the full history.

During Sprint 7 (2026-06 to 2026-07), the project pivoted to a different
autonomous research approach: **Hermes Agent** (by Nous Research), an
LLM-driven self-improving agent framework with a Skill System, 4-layer
memory, and MCP (Model Context Protocol) support.

### Why Hermes instead of the original approach?

| Factor | Original (Go agents + Vue UI) | Hermes |
|--------|-------------------------------|--------|
| **Autonomy** | Semi-automatic — human triggers agents via UI | Fully autonomous LLM-driven loop |
| **Flexibility** | Fixed Go workflows — adding research patterns requires code changes | Skill files (YAML+MD) define workflows — no code changes needed |
| **LLM integration** | Go-based prompt engineering — rigid | Native LLM support (Ollama/Together.ai) with Skill auto-extraction |
| **Memory** | PostgreSQL only | 4-layer (working/episodic/semantic/procedural) + ChromaDB vector store |
| **Cost control** | None | Budget controller (max_cost + max_iterations + max_llm_calls) |
| **Reflection** | Not implemented | Skill Step 9 (lineage + regime reflection) built into workflow |
| **Maintenance** | 9 Vue components + Go agents to maintain | 3 Hermes config files (skill + prompt + config) + 18 MCP tools |

## Decision

**Adopt Hermes Agent as the autonomous research layer**, replacing both:
1. The planned frontend AI UI (cancelled — see ODR-045)
2. The Go-native agent pipeline as the **primary** research path

### Architecture

```
User (natural language)
    ↓
Hermes Agent (LLM-driven, Ollama/Together.ai)
    ├── Skill: autonomous_factor_mining.md (10-step loop)
    ├── Prompt: quant-research.md (role + constraints)
    └── Config: hermes.yaml (model + memory + budget)
         ↓
    MCP Bridge (HTTP)
         ↓
Analysis Service (:8085) — 18 tools via GET /api/tools
    ├── L1-L4 Gate tools (validate_factor, compute_factor_ic, backtest.run, walk_forward_validate)
    ├── Gene Pool CRUD (list/save factors + strategies)
    ├── Data fetch (ohlcv, stocks, fundamentals)
    ├── Strategy registry
    ├── Lineage (get_strategy_lineage)
    ├── Market regime (get_market_regime)
    └── Summarization (summarize_backtest)
         ↓
    PostgreSQL + Redis (gene pool + cache)
```

### Key design principles

1. **Go backend is the sole writer**: Factor/strategy/Job writes go through
   Go-side MCP tools — Hermes never writes to DB directly.
2. **Hermes is the sole workflow store**: Skills/trajectory/preferences live
   in `~/.hermes/` — Go backend is unaware of Hermes's internal state.
3. **ID generation in Go**: `factor_id`/`strategy_id` are UUIDs generated by
   Go-side tools — Hermes doesn't generate IDs.
4. **Idempotency**: `save_factor`/`save_strategy` use UPSERT — safe to retry.
5. **Two-layer budget**: Session-wide hard cap (hermes.yaml) + per-skill
   soft default (skill input) — prevents cost explosion.

### Deprecation of Go-native agents

`pkg/ai/agents/research.go` and `pkg/ai/agents/generate.go` are marked
**deprecated** (not deleted). They remain functional for backward
compatibility but:
- New research workflows should use Hermes + MCP tools
- The `cmd/ai` service (port 8086) continues to run for legacy pipelines
- No new features will be added to `pkg/ai/agents/`
- Tests remain in place to prevent regressions

## Consequences

### Positive
- Autonomous research loop without human-in-the-loop UI dependency
- New research patterns added via Skill files (no Go code changes)
- Built-in budget control prevents cost explosion
- 4-layer memory enables cross-session learning
- LLM can be swapped (Ollama local ↔ Together.ai cloud) via config

### Negative
- Adds Hermes + Ollama as infrastructure dependencies
- LLM cost (mitigated: Ollama local = $0; Together.ai 8b = $0.0002/1K tokens)
- Research quality depends on LLM capability (mitigated: L1-L4 gates
  enforce validation before saving; human review optional at L5)
- `pkg/ai/agents/` Go code is now legacy — maintenance burden until
  eventual removal

## Lessons Learned

1. **Pivot early, document immediately**: The Hermes pivot happened over
   weeks of design discussion but wasn't formally recorded until Phase 2
   was nearly complete. An ODR should be created when the decision is made,
   not retroactively.

2. **Narrow interfaces enable testability**: Each MCP tool uses ISP-decomposed
   interfaces (e.g., `FactorPoolClient` with just `List`+`Save` instead of
   the full `*gene_pool.FactorPool`). This made the tools independently
   testable with minimal mocks — a pattern worth applying elsewhere.

3. **Two-layer budget prevents overruns**: The session-wide cap (50/$5/200)
   + per-skill default (30) model worked well in design. The explicit
   distinction between "hard cap" and "soft default" avoided the ambiguity
   that a single number would have caused.

4. **GateDecision as a contract**: Embedding `{level, passed, reason,
   recommendation}` in every L1-L4 gate tool's return value gave Hermes a
   consistent decision interface — the agent reads `passed` without
   parsing tool-specific fields. This pattern should be applied to any
   future gate-like tools.
